# UI area

Find where the rendered UI fails the people using it or drifts from its own system. Judge it against develop's [frontend and UI reference](../../develop/references/frontend-ui.md), the floor every UI edit follows; read it first. Read [visual direction](../../develop/references/visual-direction.md) and [reflexes](../../develop/references/reflexes.md) before judging whether the design is authored, [motion](../../develop/references/motion.md) before judging animation, and [native UI](../../develop/references/native-ui.md) for iOS or Android. A focus in the scope, such as typography or checkout error copy, narrows Explore to the items it names.

## Evidence

Render the scope when the project runs: a browser at a narrow and a wide viewport, in the states the flow can reach, because hierarchy, overlap, and contrast over images do not show in source. Native code needs source and simulator evidence; the web tools below do not apply. Record the viewports and states you checked, and name what you could not inspect as a gap, not a finding.

Form your own judgment before reading tool output, because the output anchors it. Then run the deterministic checks once over the scope: the project's accessibility and lint tooling; skip a tool that errors or stalls. Verify each hit in context, drop false positives, and note what the tools caught that you missed; a clean scan says nothing about hierarchy.

## Explore

- **Floor failures:** anything below the frontend-ui floor. Start from the riskiest flows (irreversible actions, user content, async work, permissions, anything that can lose input) and push each to its extremes: content (empty, longest, malformed), data (zero, one, many, stale, deleted, conflicting), network (slow, offline, timeout, retry, partial failure), input (keyboard, touch, assistive tech, rapid repeat), locale (expansion, plurals, RTL), and display (narrow, wide, zoomed, large text, forced colors). Walk the primary flow as a keyboard and screen-reader user, as a first-time visitor, and as one more person the surface serves, and name the element that failed each.
- **Hierarchy:** trace the first five seconds: what draws attention first, second, and third, and whether the primary action is obvious; blur the detail and check that the groups still read in order. Flag competing primary actions, a decision among more than four similarly weighted choices, more than five top-level navigation items or four siblings per sidebar level, an index screen asking for filter, sort, and tags at once, more than one primary and two secondary actions in view with the rest not grouped in a menu, a step that needs information remembered from another view, type roles too close to tell apart (the dominant heading under about 1.25 times the body size, unless a dense data UI separates the roles by weight and spacing), spacing that does not group (looser within a group than between groups, or less space above a heading than below), and icon-only navigation.
- **System drift:** one role rendered several ways: two looks for the same action, a state styled differently across screens, near-identical font sizes or radii with no scale, a hard-coded value repeated where a token exists, the same form row, toolbar group, or empty state rebuilt by hand, the same size, weight, and line-height or duration and easing combination repeated without a token, accent spent on inactive elements, a hover style on something inert. Call it drift only against an authority (DESIGN.md, a token file, an established component library); without one, report the inconsistency and ask which variant is canonical. Name the cause (missing token, one-off that a shared component should replace, mismatch with comparable areas, local defect) and fix at the narrowest level that removes it. Propose a shared component or token only for something used three or more times with the same intent; look-alikes with different purposes stay separate. A missing DESIGN.md, or one that no longer matches the tokens and components, is a candidate.
- **Interchangeable design:** composition, interaction, copy, or visual system that could move unchanged to an unrelated product: category defaults, the model defaults listed in reflexes, decoration standing in for real content. On task surfaces a user fluent in the category must trust the UI at once; a native app must read as native, not as a ported website. Before reporting a pattern, check its exceptions: product requirement, brand, editorial intent, data visualization, or a documented design-system choice. Report the clarity, coherence, distinctiveness, or trust a pattern costs, not that the UI looks generated, and present taste as judgment, not fact. When the tone seems wrong for the stakes, ask whether it is intended.
- **Removable complexity:** the same information shown twice, variation without purpose, everything visible at once, steps a flow can lose, modals that inline editing could replace, choices a default could make, step progress shown when the steps are not meaningful or their total is not stable, and dead CSS, unused components and variants, and orphaned assets. A removal keeps needed functionality, accessibility, and the information people decide with; removing a feature is the user's call.
- **Copy:** read the whole interaction path, not isolated strings: ambiguous labels, errors without consequence or recovery, terms that change between screens.
- **Motion:** motion on something seen tens or hundreds of times a day or started from a keyboard shortcut, motion with no nameable purpose (feedback, spatial consistency, state indication, preventing a jarring change, explanation, delight on a rare moment), motion that drops frames or restarts when interrupted, and completion, waiting, first use, or errors left unacknowledged.

## Rank

Give each candidate its evidence: file and selector, computed value, screenshot, or tool hit. Merge instances that share a cause into one systemic candidate, such as hard-coded colors in 15 components. Rank by user impact: blocked tasks, data loss, misleading state, and WCAG 2.2 AA failures first; then missing reachable states; then hierarchy, flow, responsive, and drift problems; then visual and motion inconsistency; then code and asset cleanup. Reflex patterns rank with visual inconsistency unless they harm use, trust, accessibility, or coherence. Between two ranks, ask whether a user would contact support about it; if so, take the higher. When the concept itself fails, present a redesign as one candidate instead of a list of patches. Before your recommendation, add a `Keep:` line naming the two or three things that work and must survive.

## After the choice

The user's choice authorizes a candidate inside the existing visual world (floor failure, missing state, copy, drift, consolidation, removal): load the `develop` skill through the Skill tool, or your runtime's equivalent, and implement it with its UI references. Fix the observed issues as one batch, adding no features or animation to make the pass look substantial. Verify with the bounded rounds in the frontend-ui reference, marking each fix resolved, partial, or unresolved; a fix you cannot see in the new render is unresolved, and one that moved without gaining the quality it named is partial. Start no new hunt in the re-check, and let screenshots the user supplied outrank your own. Report before-and-after evidence, and for a removal, each removed option and whether it needs another access point.

Other candidates need a decision first:

- **New design system:** confirm its location, ownership, and adoption scope with the user.
- **DESIGN.md:** load the `research` skill and follow the design-system section of its documentation reference.
- **Redesign or new direction:** suggest `/prototype` variations on the route, because a direct rebuild replaces an identity the user has not chosen.
- **Change to what the product does** (offline support, collaboration, new backend capability): load the `interview` skill; it is a product decision, not a UI fix.
